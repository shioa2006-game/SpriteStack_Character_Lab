# 画像からのキャラクター生成 比較分析：実験01 MAREN と実験02 CRYSTAL MAGE

## 結論

2つの実験は、参考画像の読み取りから公開PNGまで、同じ6段階の工程をたどった。共通エンジン（`spritestack/`）は両方とも無変更。キャラクター固有の部分は、ほぼモデル生成コードの形状部分と、配色・寸法・描画順の判断に集まる。

- **重複。** 形状の基本関数（`paint`、`ellipsoid`、`capsule`）、モデル生成の `main`、MARENの攻撃の転用（BRAMからの複写）は、複写元と一字一句同じ。静止用のベイク、検証、比較図も70〜97%が似た複写になっている。共有されているのは、色抽出の関数1つ（CRYSTAL MAGEがMARENの `extract` を読み込む）だけ。
- **固有部分。** `build()` の形状記述は両者の類似度0.20で、ファイルの83〜86%を占める。参考画像の特徴はここに入る。共通化すべきではない。
- **判断と試行錯誤。** 試行の大半は、48 pxで特徴が潰れる、色が隣と同化する、特定の方向で特徴が隠れる、という3種類だった。両実験で繰り返した問題は、設計規則として先に適用できる。例：外套の薄い殻から裏地が点状に透けた件は、両方で起きた。
- **自動検証。** CRYSTAL MAGEで追加した汎用の検査（つながり、手と装備の接触、再描画との一致、反転の否定、画面上の左右）を、MARENにも読み取り専用で適用した。すべて合格し、隠れた33ボクセルの部位の切れ端を1つ見つけた。検査はキャラクターをまたいで使える。
- **共通化の提案。** 価値が高い順に、①画像由来キャラクター用の汎用検証、②静止だけのベイクの共有、③形状の基本関数の共有、④配色と寸法の事前検査。どれも、既存のNPZとPNGが変わらないことを回帰の条件にする。体形テンプレートや衣装の自動生成は、キャラクターが似通う危険が大きく、優先度を下げた。

新しい参考画像からの制作手順は [CHARACTER_CREATION_GUIDE.md](CHARACTER_CREATION_GUIDE.md) にまとめた。

## 調べ方

- 対象：[実験01レポート](IMAGE_TO_CHARACTER_01.md)、[実験02レポート](IMAGE_TO_CHARACTER_02.md)、両キャラクターのコードと設定（コミット `cfef769`、`9c99f99`）、検証・比較スクリプト。
- コードの類似度は、関数ごとのソースを Python の `difflib.SequenceMatcher` で比べた比（1.00 が完全一致）。
- CRYSTAL MAGEの検証にある汎用の検査を、MARENのモデルと公開PNGに読み取り専用で適用した。スクリプトは無視される `.phase1/` に置き、コミットしていない。
- 既存のコード、設定、モデル、PNGは変更していない。

## 4. キャラクター固有の造形として残すべき処理

- **`build()` の形状記述。** 髪の毛束の数・向き・太さ、衣装の殻の形、裾の高さ、装備の形状。類似度0.20で、参考画像の特徴そのもの。
- **描画順。** MARENはベルトを胴の後に塗った。CRYSTAL MAGEはマントを「鐘形→腕→肩の覆い」の順に塗り、拳を杖の後に塗った。どこが前に出るかは造形の判断。
- **部位の所属。** 髪は頭。外套やチュニックの裾は、MARENでは骨盤、CRYSTAL MAGEのマントは胸に所属させた。動かしたときの破綻の仕方が変わる。
- **配色の調整。** 抽出色の調整は、隣り合う色との関係で決まる。MARENは外套を明るくし、CRYSTAL MAGEは髪を暗く、マントを明るくした。向きが逆で、規則では決まらない。
- **関節座標と立ち姿。** 頭身、肩・股関節・膝の高さ、手の位置、杖の握り位置。
- **装備の作り。** 剣・盾と杖・本では形も持ち方も違う。取り付け枠と目印だけを共通にする。
- **補完の判断。** 背面、側面、隠れた部分の推測。根拠をレポートの「確認／推測／未再現」表に残す。

## 8. 共通化によって品質が低下するリスク

| リスク | 例 | 対策 |
| --- | --- | --- |
| キャラクターが似通う | 体形テンプレートや「マント」関数を作ると、全員が同じ鐘形・同じ頭身になる。LARK、BRAM、MAREN、CRYSTAL MAGEは比率が大きく違う | 共有するのは基本形状と検査まで。衣装や体形の部品は共有しない |
| 共有関数の変更が全キャラクターを変える | `capsule` の境界の扱いを1つ変えると、全NPZと公開PNGが変わる | 共有関数の挙動を固定し、全キャラクターのNPZ一致を回帰条件にする |
| 配色の自動補正が参考画像から離れる | 明度差の規則で自動的に明るくすると、MARENの外套とCRYSTAL MAGEの髪で調整の向きが逆になる | 自動補正はしない。警告と出典の記録だけにする |
| しきい値を合格に合わせる | 「結晶 ≥ 3 px」は通っても、結晶に見えるとは限らない | しきい値はキャラクター設定に置き、変更理由を記録。目視の評価を省かない |
| 描画順の一律化 | 「装備→手」「衣装→腕」を固定すると、握りや肩の覆いの表現が崩れる | 描画順はモデル生成コードに残す |
| 静止専用ベイクとCLIの形式のずれ | 共有ベイクのメタデータがCLIの形式から離れると、ギャラリーやゲームが読めなくなる | CLIと同じメタデータ形式を検査で照合 |
| 共通化に時間をかけて試行の回数が減る | 仕組みの整備を優先すると、見た目の反復が後回しになる | 共通化は回帰で守れる範囲から。見た目の反復の時間を先に確保 |

## 9. 実装する価値がある共通機能（提案）

今回は実装していない。優先順に並べる。

### 提案1：画像由来キャラクター用の汎用検証

- **期待する効果。** MARENにはない検査（つながり、接触、再描画、反転、投影の左右、迷い画素）を全キャラクターに広げる。読み取り専用の適用で、MARENの隠れた切れ端を1つ見つけた。新キャラクターの検証スクリプト（実験02で260行）の大部分が不要になる。
- **実装範囲。** `research/` に、設定ファイルのパスと小さな品質設定（主装備・副装備の部位、可視画素の下限と方向、公開先）を受け取る検証を置く。既存の `verify_maren.py`・`verify_crystal_mage.py` は残し、同じ結果になることを確認してから置き換えるか判断する。
- **副作用。** しきい値の設定が増える。キャラクター固有の検査（MARENの攻撃の転用規則など）は別に残る。
- **検証方法。** MARENとCRYSTAL MAGEで実行し、既存の検証と同じ合否になることを確認する。わざと壊したモデル（装備を手から離す、殻を薄くする、1方向を反転で差し替える）で失敗することを確認する。

### 提案2：静止だけを焼く共通の手段

- **期待する効果。** 2つの `bake_idle.py`（類似度0.48〜0.96）を1つにする。出力形式のずれを防ぐ。
- **実装範囲。** 次の2案のどちらか。(a) 共通CLIに焼くモードの指定（例：`--modes idle`）を加える。(b) `research/` か `characters/` の共通の場所に、静止と比較用の解像度を焼くモジュールを置く。(a) はエンジンの変更になる。
- **副作用。** (a) はLARK・BRAMのCLIの契約を変える。MARENとCRYSTAL MAGEのREADMEのコマンドが変わる。
- **検証方法。** 共通の手段で焼いたMAREN・CRYSTAL MAGEのPNGとJSONが公開素材とデコード後に一致すること。LARKの `verify_rebuild.py` とBRAMの `verify_bram` が合格すること。

### 提案3：形状の基本関数の共有

- **期待する効果。** `paint`、`ellipsoid`、`capsule`、`tube`、向きのある箱、殻の生成を1か所にまとめる。殻の厚さや細い軸の最小半径の規則を関数側で警告できる。
- **実装範囲。** 基本関数だけのモジュール。衣装や体の部品は入れない。既存キャラクターのコードを書き換えるかは別に判断する。
- **副作用。** 関数の挙動を変えると全キャラクターのNPZが変わる。共有後は挙動を固定する必要がある。
- **検証方法。** 共有関数を使って生成したMAREN・CRYSTAL MAGEのNPZが、コミット済みのNPZと完全に一致すること。

### 提案4：配色と寸法の事前検査

- **期待する効果。** 両実験の反復の多くを、焼く前に警告できる。
  - 配色：各材質の基色と輪郭色の明度差。指定した組（髪と衣装、肌と明るい布、装備と背後の色）の明度差。
  - 寸法：方向ごとの外形の余白と、上限を決めている部位（例：Wの杖頭）。殻の外層の厚さ。細い部位の最小の幅。
- **実装範囲。** 設定とNPZを読み、警告を出すだけの検査。合否で止めない。
- **副作用。** 明度差の数値は色相の違いを捉えない。警告を無視する運用になりやすい。
- **検証方法。** 両実験の抽出色（調整前）で警告が出て、採用色で警告が減ることを確認する。CRYSTAL MAGEの初回モデル相当の薄い殻と細い軸で警告が出ることを確認する。

### 提案5：読み取りの補助

- **期待する効果。** 採色範囲と目印の座標を決める時間を減らす。
- **実装範囲。** 参考画像に格子を重ねた拡大図と、範囲を描き込んだ確認図を `.phase1/` に出す。実験02では一時的なコードで作った。
- **副作用。** ほぼない。出力は追跡しない。
- **検証方法。** 両実験の `reference_regions.json` を描き込み、範囲が意図した材質に乗っているか目視する。

### 提案6：比較図の共有

- **期待する効果。** 2つの `compare.py`（関数の類似度0.69〜1.00）を1つにし、レポートの図をそろえる。
- **実装範囲。** キャラクター名、装備の可視材質、比較対象のシートを引数にした比較図。
- **副作用。** 既存レポートの図を作り直すと見た目が変わる。既存の結果は残す。
- **検証方法。** 両実験の計測JSONが、既存の `metrics.json` と同じ値になること。

### 提案7：攻撃の転用関数の一般化

- **期待する効果。** BRAMとMARENで同一の `retarget` を1つにする（実験01の提案）。
- **実装範囲。** 設定ファイルのパスを引数にする。
- **副作用。** BRAMの攻撃クリップの生成経路が変わる。
- **検証方法。** BRAMとMARENの `attack_motion.json` が再計算で同一になること。`verify_bram` の合格。

### 優先度を下げたもの

- **比率からの関節座標の自動決定、衣装の部品化。** 8. のとおり、キャラクターが似通う危険が大きい。読み取りの自動化（領域分割による採色範囲）と合わせて、別の研究として扱う。
- **マント・裾の従属部位。** 価値は大きいが、エンジンの姿勢計算と再スライスの変更が必要。[実験02レポート](IMAGE_TO_CHARACTER_02.md#マントや裾を動かす場合の研究課題)の課題として扱う。
